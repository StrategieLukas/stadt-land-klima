# Search coverage audit

Public Nuxt landing pages and published job descriptions now join the existing content search index. Search intentionally excludes private workflows and CMS infrastructure. Public tools, event series, tours/stops and individual Wahlcheck entries still need dedicated documents; municipality lookup already uses separate search providers.

## Directus collections

The development metadata inventory on 18 November 2026 contains **83 collections: all 54 repository-managed collections (47 tables and 7 navigation folders), plus 29 system collections**. There are no extra or missing managed collection names relative to `src/directus/schema/collections`. Development Meilisearch contains one index, `site_content`; no separate local collection indexes exist.

“Indexed” describes an explicit projected subset, never all collection fields. “Public gap” identifies content displayed publicly that is not yet searchable as its own record. Relation/configuration/private rows do not need independent documents.

## Index freshness and privacy

Full reconciliation uses the private Frontend-Server identity, selects explicit fields and completes every source read before mutating `site_content`. A failed source read must not prune a partial snapshot. Published jobs now participate in that same snapshot. No permissions or CMS schema changes are needed for indexing them.

The existing Directus hook immediately synchronises pages, supported blocks, news, events, articles, measures and opted-in users. New jobs and public route entries refresh on Nitro startup and scheduled reconciliation (15 minutes in development, one hour in production). Jobs do not yet have an incremental Directus hook. Unpublished/deleted jobs and stale job slugs are nevertheless rejected by the live publication/URL check before the API returns cached hits. Reconciliation removes their obsolete documents. Description changes can remain cached until refresh, as with other periodic cache refreshes; do not treat indexed text as an access-control boundary.

Static organisation team entries remain hardcoded. A future change should read `organisation_teams` through its public field projection, use real team keys and validate anchors against that collection before returning hits. Public tools, event series, tours/stops and eligible election detail entries are the remaining first-class collection gaps. They require dedicated extraction plus matching live visibility checks, rather than blanket collection indexing.

## Regression coverage

Existing targeted automation in `bin/test_suite/src/searchReconciliation.test.ts` covers shared reconciliation, publication, orphan blocks, live visibility, stale URLs and opted-in users. `phase6.test.ts` covers the live search API, type-filter validation and sanitised highlights. The new route catalogue, job extraction/live filtering, and this collection inventory have **no dedicated automated regression coverage**. Existing test harness imports were kept compatible. Tests, browser checks, full readiness checks and container builds were skipped at the user's request; native and deployed acceptance remain pending.

## Dependency review

A read-only frontend `npm audit` on 18 November 2026 reports **60 affected packages: 50 high and 10 moderate**, with no critical advisories. The direct advisory entries concern `picomatch`, `glob` and `minimatch`; affected dependents account for the larger package count. This search change introduces no dependencies and does not alter dependency declarations or lockfiles. Development startup regenerates the translation artifacts before Nuxt loads them. The other CLI/extension dependency trees were not audited in this change. Dependency remediation remains separate work; the audit does not establish runtime exploitability for each affected dependent.
