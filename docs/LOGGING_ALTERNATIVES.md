# Logging component choices

The selected integration is **host journald → Vector → HTTPS gateway → VictoriaLogs →
existing Grafana**, alongside VictoriaMetrics metrics. The user selected Vector
and VictoriaLogs after comparing collection footprint, filtering and resilience.
The prepared Vector config has a stable bounded disk buffer, acknowledgments and
backpressure. This improves restart recovery; it is not an exactly-once audit
archive. Review [current release findings](LOGGING_SECURITY_REVIEW.md) before
activation. The other entries remain alternatives, not installed components.

Resource rankings below are architectural expectations, not measurements of SLK
traffic or guarantees. Compare idle RSS, CPU, disk writes, ingest throughput,
query latency and recovery using representative logs on the intended machines.
Memory limits are safety budgets, not predictions of normal usage. A smaller
binary or memory-safe implementation alone does not establish better security.

The supplied implementation uses Vector's HTTP JSON-lines sink and VictoriaLogs'
`/insert/jsonline` endpoint, plus the separate VictoriaLogs Grafana plugin. The
Loki/Alloy prototype configuration has been removed. VictoriaLogs also supports
native systemd-journal-upload with server-side ignored fields; filtering before
transmission and consistent application severity are reasons to keep Vector here.

## Transport and placement

| Choice                                                     | Benefits                                                                                                                  | Cost / risk                                                                                                                                                                                                                                                        |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **HTTPS + per-host Basic auth at existing Caddy** — reused | Reuses the proxy/TLS stack; no new application-host listener. Separate ingest-only usernames support targeted revocation. | Password rotation and gateway rate/body controls need ownership. TLS is mandatory. Caddy hashes remain protected; `X-Scope-OrgID`/labels do not authenticate a sender.                                                                                             |
| **mTLS**                                                   | Machine certificates can provide strong client identity without reusable passwords.                                       | CA issuance, renewal, expiry monitoring and revocation are additional operating responsibilities. Bind certificate identity to authorization; a valid certificate alone need not imply access to every tenant/API.                                                 |
| **Existing private VPN + HTTPS**                           | Reduces internet reachability and can reuse an established administrative network.                                        | VPN peers and keys become another trust boundary. A private network alone is not authorization; retain authentication and enforce routes. Adding a new VPN solely for logging adds another daemon/control plane.                                                   |
| **Host service** — reused                                  | Direct journal read permission and systemd credentials; avoids runtime socket/mount plumbing.                             | Journal membership grants broad read access. Sandbox and dedicated identity are important. Loopback is reachable by local processes; it is not per-user authentication.                                                                                            |
| **Collector container**                                    | Reproducible image packaging and familiar container resource controls.                                                    | Journal mounts/group mappings and cursor storage need care. Rootless journal access can be awkward. Engine sockets confer substantial control and are unnecessary here. An image is not automatically a smaller privilege boundary than the supplied host service. |

The selected default is **Vector + VictoriaLogs**, with a native unprivileged
collector service, a 1 GiB disk buffer and private metrics. Fluent Bit remains a
reasonable lower-footprint candidate if actual resource measurements justify a
switch. Vector still needs release/dependency maintenance; the selected package
is not certified vulnerability-free by the configuration choice.

## Acceptance before deciding

Use the same representative traffic for each candidate. Include plain text, large
JSON entries, bursts, malformed records, token-bearing canaries that must stay
redacted, and expected service/severity fields. Measure normal/peak RSS/CPU,
bytes/day, disk growth, dropped/retried entries and typical query latency. Block
the receiver, restart the collector, fill its buffer to the configured limit,
restore connectivity, and count missing/duplicate records. Test monitoring-disk
failure/recovery separately. A collector's ready endpoint alone is insufficient.

The supplied runbook proposes 30-day central retention and a bounded local
journal; longer retention or audit-grade availability should be explicit targets.
Memory limits and one successful canary do not establish these targets.
