## Host, database and secret hardening

These original S10/operator findings are not resolved merely by updating runtime images:

- Move application database access to a least-privilege non-superuser role, with a separate migration/admin identity where needed. Test schema-import and extension requirements before changing grants.
- Replace known/example signing, admin and database credentials and define session invalidation on rotation. Review production secrets independently of local example files.
- The development PostgreSQL configuration still needs exposure review; do not assume production loopback restrictions also protect a development `0.0.0.0:5432` binding. Bind to loopback or enforce appropriate host/network restrictions.
- Review code/upload/temp directory ownership and minimum writable paths; make extension code read-only where feasible. Never solve PDF/Docker permission errors with recursive/world-writable `chmod 777`.
- Protect backups and environment files, verify restoration and monitor disk, memory, request failures and rate-limit/CSP reports. Resource caps bound load but do not prove denial of service impossible.
