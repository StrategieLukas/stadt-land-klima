> Historical checkpoint. This records the editor-migration checkpoint. Later work completed the checked persistence/publication boundaries and website session BFF; historical remaining findings below are not the current backlog. Current status: [implemented hardening](SECURITY_HARDENING.md) and [remaining work/decisions](REMAINING_TODOS.md).

Reviewed on 2026-10-21. The frontend now pins `@blokkli/editor` to **2.0.0-alpha.73** (published source revision `af4afcea9ee9c7667b1545b02de841ee09828463`). The follow-up toolchain upgrade pins Nuxt **4.6.2**, Vite **8.3.5** and TypeScript **6.0.3**; Directus remains **11.17.4**. See [SECURITY_HARDENING.md#framework-editor-and-typescript-phases](SECURITY_HARDENING.md#framework-editor-and-typescript-phases) for that upgrade and its current validation. This is an alpha editor release, not a stable 2.0 release.

## What changed

The Directus adapter was migrated first. It uses the new editor imports, authenticated current-user and effective-permission APIs, bundle permissions, publish metadata, drag-event payloads, reference-field configuration and searchable library filter arrays. Multiple-block moves now retain their order and target the specified nested field. Deleting published blocks still uses the existing archive transaction and therefore requires update permission rather than permission to hard-delete rows.

The existing Directus persistence extension remains the publication boundary. Draft ownership, local recovery, server recovery, cross-tab preview polling, atomic publishing and revision-conflict checks retain their existing protocol. No schema, role or public permission changes are required.

V2 requires `isVisible` on both root and nested blocks. The shared mapper supplies it when reading V1 content, preserving explicit false values, UUIDs, options, markup and unrelated prop arrays. The editor additionally requires `editContext` for selection and actions: it is derived on isolated mapped copies, never written into saved content or drafts. New blocks, duplicates and reusable-block copies receive visibility flags and fresh UUIDs where appropriate.

The provider now supplies V2 view/edit permissions. Existing block components retain their bundles and rendering, use the compile-time `import.meta.blokkliEditing` flag and declare editable, droppable and nested prop mappings. The discovery glob now resolves through `~/`; the previous relative pattern silently omitted application blocks in V2. Icon options were adapted to the V2 option schema.

The public blocks endpoint now includes UUIDs and options. Both are necessary for reliable anonymous SSR and preserving the appearance of published content. The prior claim that public blocks intentionally do not render was incorrect; regression tests now assert their rendered HTML.

The old Blökkli 1.3.4 version-guard patch and `patch-package` dependency were removed. Postinstall runs `nuxt prepare`.

## Remaining work and risks

1. **Nuxt upgrade completed in the follow-up change.** Nuxt 4.6.2/Vite 8.3.5 build and run with the editor. The lockfile/native-dependency problem was corrected; no mandatory platform binding is needed. All seven direct Nuxt advisories from 4.4.8 are removed. The earlier blanket unreachability assessment was too broad, including a confirmed development disclosure that now returns 403.
2. **Do not force Vite 7 into a newer Nuxt builder that requires Vite 8.** The investigated Nuxt 4.6.2 builder imports `transformWithOxc`, which Vite 7 does not export. Keeping mismatched Nuxt/builder versions is not a supported solution.
3. **Dependency audit remains open.** The current framework audit reports 17 affected package entries (14 high, 3 moderate); the seven direct Nuxt advisories are gone but transitive chains still flag the framework. They include the Nuxt chain, build-time `micromatch`/`braces`, `node-forge`, and the alpha's newly installed `mammoth` peer chain through `argparse`/`sprintf-js`. The normal production output does not contain that Mammoth chain, but the dependency finding remains; optional document-import features must be assessed before enabling them. Do not hide findings with broad overrides or downgrade the editor automatically to satisfy audit suggestions.
4. **Track the alpha.** Keep the exact version and lockfile together. Revalidate subsequent alphas/stable releases against the adapter and browser suites before updating.
5. **TypeScript work remains.** Broad SDK casts and existing application diagnostics belong to the later migration phases; a successful production build is not a clean type check.
6. **Public-block access repaired in the October 22 audit.** The earlier endpoint allowed draft blocks and omitted parent checks. It now delegates to `server/utils/publicBlocks.ts`, requires an explicit supported parent scope and a published block on a published parent; tour reports additionally require the published stop/report/tour hierarchy. `publicNavigationFlow.ts` rejects unscoped requests, published blocks on draft pages/news, and draft blocks on published pages, while preserving public SSR and nested chart content. No public-role permissions were broadened. See [SECURITY_HARDENING.md#framework-editor-and-typescript-phases](SECURITY_HARDENING.md#framework-editor-and-typescript-phases).

## Deployment and rollback

Deploy the frontend code, package manifest and lockfile together using the normal clean-install/build process. No Directus import or content rewrite is needed. Existing V1 records remain readable through the runtime mapper. Build and test before deploying; the version is still alpha.

For rollback, restore the previous frontend adapter, provider, block components, shared mapper, Nuxt config, package manifest, lockfile and the old patch together, then perform a clean install/build. Do not mix the V1 adapter with the V2 package. The new visibility flags are additive; runtime editor context is not persisted.
